## RTS 的困局：一个被自己门槛杀死的品类

RTS 品类有一个广为人知的矛盾：**它的核心魅力（多线并发的系统调度与宏观资源博弈）和它的核心痛点（APM 门槛过高）是同源的。**

星际争霸的职业选手 APM 在 300-400，相当于每秒 5-7 次有效操作。普通玩家可能在 80-120。这种情况下，RTS 的部分核心体验对普通玩家来说是"关闭的"——原因通常在于操作门槛而非策略深度。

这个问题在面试中被反复问到："如果在今天让你做一款 RTS，你会怎么改？"

本文分享的是《补给战争》——一份把"物流网络"作为核心机制的原创 RTS 策划案。拆解它的三个核心设计：**动态难度双轨系统、物流闭环经济、以及支撑千单位同屏的 ECS 架构选型**。

---

## 一、核心设计哲学：把 RTS 的门槛从"手速"降回"策略"

《补给战争》最根本的设计决策是：**弱化微操，深化物流与宏观指令。**

传统 RTS 的操作负担来自：
- 每个小兵需要手动控制走位
- 多线作战需要频繁切屏
- 农民的生产分配需要实时手动调整

《补给战争》的处理方式：
- 玩家不直接控制每个单位的走位和攻击——**通过全局"指挥官面板"下达宏观指令**，如"区域清剿""据点固守""优先摧毁敌方补给线"
- AI 自动完成微观执行——寻路、交战、站位
- 玩家的真正挑战在于**战略层的资源分配**：有限的农民人口，是派去上前线打仗，还是留在后方维持补给线？

这就把 RTS 从"APM 竞赛"变成了"资源统筹竞赛"——而后者更接近 RTS 的核心乐趣所在。

## 二、动态难度双轨系统：FD（明线）× Dread（暗线）

这是《补给战争》系统设计中的重要部分——如何在一款有成百上千单位、局势瞬息万变的 RTS 中，保证数值不崩坏且难度曲线始终维持在最佳心流区间？

### 2.1 问题：传统刷怪时间轴的三宗罪

大多数 RTS 或 PvE 策略游戏的难度控制基于**静态时间轴**——第 5 分钟刷 3 队小兵，第 10 分钟刷 1 个 Boss。

问题：
1. **无视玩家状态**——玩家经济崩了也照刷不误，雪上加霜
2. **缺乏负反馈**——没有"防止滚雪球"的机制，赢了就一直赢，无聊
3. **缺乏正反馈调节**——没有"落后者追赶"的机制，输了就只能等死

### 2.2 明线：森林扰动值（FD）——"高收益伴随高风险"

FD（Forest Disturbance）是一个**事件驱动的全局变量**：

```
FD = Σ(玩家行为 × 行为权重) × 扩散系数

玩家行为包括:
  - 砍树:    +5 FD / 次
  - 采矿:    +8 FD / 次
  - 造兵:   +15 FD / 单位
  - 建造建筑: +20 FD / 建筑
  - 战斗击杀: +10 FD / 击杀

扩散: FD 在网格地图上向相邻格扩散，扩散速率与地形类型相关
```

FD 的核心设计意图：**玩家的经济行为（采集、建造、暴兵）会产生"扰动"，这个扰动会被系统量化并转化为敌人（亡灵 AI）的兵力强度。**

总威胁值（TV）的计算：

```
TV = BaseThreat + FD × ThreatMultiplier + PlayerPower × ScalingFactor

其中:
  BaseThreat = 波次基础兵力
  ThreatMultiplier = FD 到兵力的转换系数
  PlayerPower = 玩家当前的总战力评估（军队数量 × 单位强度）
  ScalingFactor = 根据难度档位调整的比例
```

这体现了"高收益伴随高风险"——你开发越多资源、建造越多部队，敌人也会越强。玩家需要在这种动态博弈中找到"最优开发节奏"，而不是无脑暴兵。

### 2.3 暗线：恐惧值（Dread）——隐形的动态阻尼器

FD 解决了"难度跟随玩家"的问题，但它有一个局限性：**如果玩家一开始就崩了，FD 不会因此降低——它只会随着玩家的经济活动增加。**

Dread 系统正是为处理这种情况设计的。

Dread 是一个**全局的隐藏变量，不对玩家展示**，只做两件事：

**失败保护（隐性救济机制）**：
```
if (player.main_base.health < 25% AND dread_flag_crisis == true):
    → apply_global_debuff_to_enemies(
        debuff: AttackPower -15%,
        duration: 90 seconds,
        label: "Dread_LastStand"  # 隐藏标签，UI不显示
      )
    → dread_flag_crisis = false  # 冷却 120 秒，防止滥用
```

**膨胀遏制（反雪球机制）**：
```
if (player.unit_production_rate_5min > ΔP_max):
    → trigger_bonus_elite_wave(
        wave_type: "Dread_Surge",
        intensity: (actual_production_rate / ΔP_max) × 1.5
      )
    → log_to_system: "Dread_Surge_Triggered"
```

Dread 系统的设计要点：
- **玩家不会看到它**——它不在任何 UI 上显示，不产生任何文字提示
- **它的存在通过"游戏体验"间接感知**——"这局差点死了，但莫名撑过来了，好险"
- **触发条件严格且不重复**——避免让玩家形成"反正有 Dread 兜底"的心理预期

### 2.4 为什么是双轨？

单用 FD（明线）→ 玩家会精确计算 FD 的积累速度 → 难度变成"可预测的" → 失去紧张感

单用 Dread（暗线）→ 玩家感知不到难度变化的规律 → 可能觉得游戏变化缺乏规律 → 失去掌控感

**双轨结合：玩家可以感知到 FD 带来的"有规律的难度递增"，而 Dread 作为隐形的阻尼器只在极端情况下介入——两者共同把难度锁定在心流区间内。**

这与经济学中"市场经济（明线）+ 央行调控（暗线）"的双轨逻辑同构。

## 三、伤害公式选择：为什么选择除法？

《补给战争》的伤害计算涉及多个叠加维度——将领光环、地形加成、补给效率——如果用减法公式，复杂性会爆炸。

我选择的公式是：

```
FinalDamage = BaseDamage × DefenseFactor × TerrainMultiplier × SupplyEfficiency × CritMultiplier

其中:
  DefenseFactor = DEF / (DEF + 85 × Level + 400)
  TerrainMultiplier = 1.0 (平地) / 0.85 (高地) / 1.15 (低地)
  SupplyEfficiency = 1.0 (补给充足) → 0.5 (补给被切断)
```

设计考量：

1. **DefenseFactor 保证边际收益递减**——无论装甲叠多高，免伤比例无限趋近于 1 但不等于 1。这让"堆防"持续有效但不无敌。
2. **多个独立乘区保证每个策略维度都被玩家感知**——截断敌方补给让 SupplyEfficiency 从 1.0 跌到 0.5，这是一个直接的 50% 伤害削减，玩家不需要理解复杂公式就能直观看到"截补给线 = 敌方变脆了"
3. **乘区之间不可互相替代**——你无法通过堆更高的攻击力来弥补被截断的补给线（因为它们是独立的乘法关系），这要求玩家关注每一个策略维度

## 四、Mass AI（ECS 架构）——当行为树装不下千单位

RTS 的同屏单位数量（数百到上千）给 AI 架构提出了一个 ACT 或 ARPG 不会面临的问题：**如果你用传统的 Actor + 行为树（Behavior Tree）来驱动每个单位，CPU 会很快成为瓶颈。**

一个简单的估算：
- 1 个单位 × 行为树 Tick = ~0.05ms（乐观估计）
- 1000 个单位同时 Tick = ~50ms/帧
- 60fps 的帧预算是 16.67ms → **已经爆了三倍**

### 4.1 ECS 的基本抽象

UE5 的 Mass AI 框架基于 ECS（Entity-Component-System）架构，把传统 Actor 的"对象 → 对象"模型重构为：

```
Entity（实体）    — 只是一个 ID，没有任何逻辑
Fragment（数据片段）— 实体的纯数据：血量、位置、补给状态、当前指令
Processor（处理器）— 批量遍历所有含特定 Fragment 的实体，执行逻辑
```

### 4.2 在《补给战争》中的应用

一个具体的例子——物流系统：

**传统做法（Actor）：**
```
每个农民是一个 Actor → 每个 Tick 检查：
  - 我现在在干嘛？
  - 采集目标还在不在？
  - 背包满了吗？
  - 该送到哪个仓库？
→ 100 个农民 = 100 个 Actor，每个独立 Tick
```

**ECS 做法（Mass AI）：**
```
FMassFarmerFragment:
  - TaskState: IDLE / HARVESTING / TRANSPORTING
  - CurrentResourceNodeID
  - CargoAmount
  - TargetDepotID

UProcessor_Logistics::Execute(FMassEntityQuery& Query):
  1. 一次性取出所有含 FMassFarmerFragment 的实体
  2. 按 TaskState 分组批处理：
     - IDLE → 查找最近资源节点 → 分配
     - HARVESTING → 检查节点是否耗尽 → 切换状态
     - TRANSPORTING → 更新路径 → 检查到达
  3. 所有农民的物流逻辑在 ONE PASS 中完成
```

关键差异不是语法上的——是**数据排布和缓存效率**：
- Actor 模型：每个单位的数据分散在内存各处 → Cache Miss 频繁
- ECS 模型：所有农民的数据连续存储 → 处理器一次遍历全部命中 L2/L3 Cache

### 4.3 为什么策划需要理解这个？

一个面试官问过我的问题："作为策划，你了解 Mass AI 这种底层架构有什么意义？"

我的回答是：**因为系统的架构约束会反向塑造你的设计边界。**

如果我知道引擎的 AI 框架是基于 ECS 的批处理模型，我在设计"物流网络"时就会：
- 把农民的决策逻辑设计成**有限状态机（而非复杂的模糊逻辑）**——因为 FSM 适合批处理
- 把物流任务抽象为**数据标签（Tag）而非行为脚本**——让 Processor 能高效分组和路由
- 清楚地知道"一千个农民"的性能开销上限在哪——从而在设计时就知道我的玩法规则能在什么规模下运行

**设计文档既需要让程序知道"你要做什么"，也需要让程序知道"你理解他需要怎么做"。** 这就是为什么我的《补给战争》策划案里附带了 GAS 数值原型和 Mass AI 技术参考——目的在于消除信息损耗。

## 五、策划的技术附录：消除从文档到代码的"翻译税"

最后讨论一个容易被忽略的点。

传统的策划文档是这样写的：
> "这个英雄有一个光环，能加周围友军的攻击力。"

程序员看到就会问：加的是基础攻击还是最终攻击？光环范围怎么判定——球形还是圆柱？多人光环叠加是加法还是取最大值？光环在英雄死亡时还在不在？

这些问题如果在文档里没回答，程序员就要自己去猜——或者来回找你确认。每一次"确认"都是管线效率的损耗。

策划在文档里附带技术附录的意义在于：**用程序的术语写清楚数据结构。**

```
光环系统 - 技术规格:

Attribute:
  - 光环加成属性: BaseAttackPower（加在 AttributeSet 的基础攻击上，非最终伤害）
  - 加成方式: Add, Magnitude = 15.0

GE 定义:
  - 类型: Infinite GameplayEffect
  - 挂载位置: 英雄自身的 ASC (AbilitySystemComponent)
  - 效果: 为范围内（球形 Radius=600）所有友方 Actor 的 ASC 应用一个
          Infinite GE_Aura_Buff

边界条件:
  - 多个光环叠加: 取最高值（而非累加），防止组队时数值爆炸
  - 施法者死亡: 光环立即移除（通过 OwnerDeath Tag 触发 RemoveOnTagAdded）
  - 范围判定: 每 0.5s Tick 一次，离开范围后 Buff 保留 2s（防止边缘抖动）
```

这份文档到代码的翻译损耗降到最低。

## 六、总结：一个策划案应该长什么样

《补给战争》的完整策划案包括了：

1. **核心玩法设计**——物流网络 + 宏观指令驱动的 RTS
2. **动态难度系统**——FD（明线事件驱动）+ Dread（暗线阻尼器）
3. **数值模型**——除法防御公式 + 多乘区独立结算
4. **AI 架构选型**——Mass AI（ECS）+ 有限状态机批处理
5. **技术附录**——GAS 数值原型 + ECS 实体/片段/处理器映射表

这五个部分合在一起，才是一份"程序拿到手就能开写"的策划案。

这两种能力——**社会科学的宏观推演（FD/Dread 的系统设计）和 UE5 的底层落地（GAS/Mass AI 的技术附录）**——构成了我们在这个系列中讨论的"跨学科技术型策划"的能力模型。
