## 从一次教训说起

去年刚开始用 UE5 做塔防 Demo 的时候，我犯了一个常见的错误：把技能逻辑全部写在了蓝图的 Event Graph 里。

一开始只有三个塔，感觉还行。加到第十个的时候，光是维护"哪个塔对哪种怪物有加成"这个逻辑，我就已经在蓝图里画了三十几个分支节点。每次想加一个新机制，都不得不在已有的复杂分支上继续叠加逻辑。

那次经历让我切身体会到了管线效率的意义。**当工具迫使每加一个新东西就要重构之前的逻辑时，后续的扩展成本会急剧上升。**

这也是为什么在做 MOBA Demo 时，我花了大量时间研究 GAS（Gameplay Ability System），并最终决定用它来从底层重构整个战斗系统。

这篇文章，就是这次技术选型和实战的完整复盘。

---

## 一、为什么选 GAS？管线效率倒逼的技术选型

做 MOBA 战斗系统时，摆在面前的大概有三条路：

| 方案 | 优点 | 致命问题 |
|------|------|---------|
| 手写状态机（蓝图/C++） | 完全可控，无黑盒 | 技能多了状态爆炸；Buff/Debuff 要自己造轮子 |
| GAS 框架（Epic 原生） | 为多人设计，内置网络同步，逻辑解耦 | 学习曲线陡峭，纯 C++，文档较散 |
| 第三方插件 | 开箱即用 | 引擎升级可能 break，生态不稳定 |

最终选 GAS 的核心原因只有一个：**它把"加一个新英雄"这件事从"写代码"变成了"配表"**。

在传统的蓝图开发模式下，一个新英雄意味着：
1. 新建一个 Character 蓝图
2. 在里面手写所有技能的逻辑
3. 手动管理 CD、Buff 计时器、伤害公式调用
4. 如果有新的 Buff 类型（比如"减攻速"），还得去所有已有英雄里检查会不会冲突

而 GAS 的架构哲学是：**Ability（技能）、Attribute（属性）、Gameplay Effect（效果）三者高度解耦**。

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   Ability     │────▶│  Gameplay    │────▶│  Attribute   │
│  (技能逻辑)    │     │   Effect     │     │   Set (属性)  │
│               │     │  (效果结算)   │     │              │
│  • 什么时候放  │     │  • 怎么结算   │     │  • 存什么值   │
│  • 放的条件    │     │  • 持续多久   │     │  • 怎么改     │
│  • 动画 Montage│     │  • 堆叠规则   │     │  • 上下限     │
└──────────────┘     └──────────────┘     └──────────────┘
        │                     │                     │
        └─────────────────────┼─────────────────────┘
                              │
                    全部通过 GameplayTag
                    进行数据驱动的路由
```

新增一个英雄的操作流程：
1. 创建一个新的 Ability 蓝图，挂上动画 Montage 和触发条件
2. 创建一个 Gameplay Effect 蓝图，配好数值（伤害、CD、Buff 参数）
3. 给这个英雄的 AbilitySet 里注册一下

**零引擎代码改动。**

这对应了业界常说的"数据驱动设计（Data-Driven）"——一种具体的、能显著降低迭代成本的技术架构选择。

## 二、三个核心抽象：Ability、Attribute、Effect 的职责边界

GAS 的核心在于"解耦"——这既是它的优势，也是学习曲线陡峭的原因。需要先搞清楚这三件事各自负责什么，才能写出清晰的逻辑。

### 2.1 Gameplay Ability（技能）

Ability 的职责是"技能执行的时序和条件"。它回答以下问题：

- 这个技能什么时候能放？（CD 好了吗？蓝够吗？没被沉默吧？）
- 放了以后播什么动画？（Montage 是哪个？）
- 中间有判定窗口吗？（AnimNotify 什么时候触发伤害？）

Ability 本身**不直接修改属性**。它的作用是"发射" Gameplay Effect。

### 2.2 Gameplay Effect（效果）

GE 是真正"改变数值"的东西。它有三种形态：

| 类型 | 持续时间 | 典型用途 |
|------|---------|---------|
| Instant | 1 帧结算 | 扣血、回蓝、瞬时位移 |
| Duration | 持续 N 秒 | 毒伤、灼烧、加速 Buff |
| Infinite | 永久（手动移除） | 装备属性加成、光环 |

GE 的另一个值得注意的设计是 **Modifier（修改器）**——它定义"怎么改属性"。比如一个"加攻击力"的 GE：

```
Modifier:
  Attribute: AttackPower
  Op: Add (+)
  Magnitude: 15.0
```

如果想做一个"叠满 5 层后引爆"的机制？GE 自带 Stacking 规则——每层叠加、叠满触发 Expiration Effect。这些在传统蓝图开发里需要手动编写计时器和计数器的功能，在 GAS 中通过 GE 的 Stacking 配置就能实现。

### 2.3 AttributeSet（属性集）

AttributeSet 是"属性的容器"。所有能被战斗系统读写的数值——血量、蓝量、攻击力、移速——都继承自 `UAttributeSet`。

设计原则：**AttributeSet 只存数据，不存逻辑**。逻辑在 GE 里，数据在 AS 里，路由靠 GameplayTag。

## 三、"机械兔"升龙拳——Z 轴判定的工程平替方案

下面是一个具体的痛点和解决方案。

### 3.1 设计需求

在 MOBA Demo 里，我设计了一个叫"机械兔"的英雄。核心技能是一招包含复杂 Z 轴位移的"升龙拳"——角色从地面挥拳上挑，在空中划出一道弧线，命中的敌人被击飞。

我的设计诉求很明确：**需要严格的三维空间判定**。站在楼梯上的敌人，如果升龙拳的轨迹没经过他的 Hurtbox，就不应该被打中。

### 3.2 第一个方案：骨骼碰撞箱

理论上最完整的做法是：在手臂骨骼的每一帧位置挂载精准的物理碰撞箱，逐帧检测碰撞。

问题：
- 一根手臂从蓄力到挥出，60fps 下大约 30 帧
- 每一帧都要在手臂、前臂、拳头三个关节分别做碰撞检测
- 一个技能 = 90 次碰撞检测
- 同屏 10 个英雄各放技能 = 管线直接炸

**开发成本高 + 性能开销大**，在实际项目中难以采用。

### 3.3 平替方案：Socket 划线检测

查阅了大量资料后，我找到了一套"降级精度、保住体验"的方案：

1. **在手臂动画的关键节点挂载不可见 Socket**：手腕、肘部、拳峰各一个
2. **用 AnimNotifyState 划定"激活窗口"**：只在攻击帧的特定区间（前臂挥出到收招前）激活检测
3. **在窗口期内，让 Socket 高频连线生成射线检测**：拳头→肘部→肩部形成一条连续的检测链

```
AnimMontage 时间轴:
├── 前摇 (0-0.3s)     — 不检测
├── ★ 激活窗口 (0.3-0.6s) — Socket 连线, 每帧 Line Trace
└── 后摇 (0.6-1.0s)   — 不检测
```

用这套方案：
- 性能开销从"O(帧数 × 碰撞体数)"降到"O(窗口帧数 × 3 条线)"
- 命中手感几乎不受影响——因为 Z 轴轨迹的核心部分（手臂上挥的弧线）被 Socket 连线准确覆盖了
- 开发成本可接受——只需要在 Montage 里加几个 Socket 和一个 AnimNotifyState

### 3.4 实践总结

**在实践中，核心目标是：在核心体验不受损的前提下，找到工程上最优的妥协路径。**

这要求对底层实现有足够的理解——能判断哪些精度可以降，哪些精度降了体验就会崩。

## 四、数据驱动管线：为什么这一点容易被忽视

回到 GAS 的话题。有一个容易被技术讨论忽略的点：**GAS 真正的价值在于它对策划工作流的解放**。

在没有 GAS 的传统管线里，做一个新英雄的流程大概是这样：

```
策划写文档 → 程序评估排期 → 程序写代码 → 策划验收 → 手感不对 → 程序再改代码 → ...
```

每一步都是跨部门沟通，每一步都有信息损耗。策划说"这个技能应该有打击停顿"，程序员反问"停几帧？在哪一帧停？停了以后怎么恢复？"——这些问题如果文档里没写清楚，就是来回拉扯。

而在 GAS + 数据驱动的管线里：

```
策划在编辑器里调 GE 参数 → 直接跑起来看手感 → 调 CD/伤害/判定窗口 → 满意后提交 → 程序不需要动代码
```

策划调整的"攻击力+15%"、"硬直时间延长 0.2s"、"Buff 叠加上限从 5 改到 3"，全部是配表操作。

这不仅提升了迭代效率，也**让设计意图减少了"技术翻译"带来的损耗**。策划脑子里想的和最终跑在引擎里的，是同一套参数。

---

## 五、总结：技术型策划的三条实践原则

回顾这个 MOBA Demo 的开发过程，我提炼出三条自己以后会持续遵循的原则：

**原则一：选技术方案时，多考虑三个月后加新东西时的扩展成本，少关注当下开发速度。**
GAS 的学习曲线确实陡，但一旦架好了，后续的英雄扩展效率是指数级提升的。

**原则二：设计和技术之间不需要争论"谁说了算"——关键是明确核心体验是什么，以及保住它的最小工程成本是多少。**
升龙拳的 Socket 划线方案就是在这个原则下找到的。

**原则三：策划能写代码的价值在于消除从文档到代码的信息损耗。**
当策划能用 UE5 的底层语言（GAS、GameplayTag、AnimNotify）来思考设计时，GDD 里的每一句话都可以直接映射到引擎管线。
